1. Introducción

Este proyecto es una API REST construida con Spring Boot 4 + JPA (Hibernate) + MySQL + Spring Security. Simula una app de listas de compra: los usuarios se registran e inician sesión, crean listas de compra y les agregan items (productos pendientes por comprar), a los que pueden cambiarles el estado (PENDIENTE → COMPRADO). Además gestiona un catálogo de productos con inserción por lotes, búsqueda y actualización.

Regla de oro de las capas: El Controller NO implementa lógica: solo expone el endpoint y llama al Service. El Service contiene la lógica de negocio y usa el Repository. El Repository habla con la BD. La flecha siempre baja: Controller → Service → Repository → BD.

2. Orden para levantar XAMPP y crear la base de datos

¿Qué es XAMPP? Un paquete que trae Apache (servidor web) y MySQL (base de datos), entre otros. Nosotros solo usaremos Apache (para entrar a phpMyAdmin) y MySQL (donde viviraá la base de tu proyecto).

Orden correcto, paso a paso

  1. Abre el panel de control de XAMPP (XAMPP Control Panel).
  2. Pulsa Start en la fila de Apache y en la fila de MySQL. Ambos deben quedar en verde (si un puerto está ocupado, verás un mensaje rojo; normalmente es porque otro servicio usa el 3306 o el 80).
  3. Desde la misma ventana de XAMPP: pulsa el botón Admin de la fila de Apache. Eso abre tu navegador en http://localhost/phpmyadmin automáticamente (no necesitas escribir la URL a mano). Si tu versión no muestra el botón, abre el navegador y escribe la URL directamente.
  4. En phpMyAdmin, en el menú lateral izquierdo pulsa "Nueva" (o "New"), escribe el nombre cibertec_demo y pulsa Crear. No hace falta elegir "cotejamiento"; deja el que viene por defecto.
  5. Recién ahora corre el proyecto en IntelliJ.
¿Por qué la base se crea ANTES que el proyecto? Con spring.jpa.hibernate.ddl-auto=create, Hibernate crea (o recrea) las tablas al arrancar la app. Pero NO crea la base de datos: la base cibertec_demo debe existir de antemano. Si corres el proyecto sin la base, fallará la conexión con un error tipo "Unknown database 'cibertec_demo'".
Ojo con ddl-auto=create: cada vez que arranques la app, Hibernate borra y recrea las tablas (los datos se pierden). Es cómodo en desarrollo; nunca lo uses así en producción.

Propósito: Archivo que Spring Boot lee al iniciar: puerto, conexión a la BD y comportamiento de JPA/Hibernate.

Mi código:

#Configuración JPA / Hibernate avanzados
spring.jpa.properties.hibernate.jdbc.batch_size=10
spring.jpa.properties.hibernate.order_inserts=true
spring.jpa.properties.hibernate.order_updates=true
spring.jpa.properties.hibernate.generate_statistics=true
spring.jpa.properties.hibernate.cache.use_query_cache=true
spring.jpa.properties.hibernate.cache.use_second_level_cache=true
spring.jpa.properties.hibernate.cache.region.factory_class=org.hibernate.cache.internal.NoCachingRegionFactory

Claves a entender

  • server.port=8080 → Tomcat escuchará en el puerto 8080. Accedes a http://localhost:8080.
  • jdbc:mysql://localhost:3306/cibertec_demo → MySQL en localhost:3306 (puerto por defecto de XAMPP) y base llamada cibertec_demo. La base debe existir antes de arrancar.
  • useSSL=false → desactiva SSL (solo desarrollo).
  • serverTimezone=America/Lima → zona horaria. Ojo: el profesor la tenía como serverTimeZone (con "zone" en mayúscula) y eso causaba problemas; la forma correcta es serverTimezone.
  • ddl-auto=create → Hibernate crea las tablas al iniciar (las borra al cerrar). Cuidado en producción.
  • show-sql=true + format_sql=true → muestra el SQL en consola, indentado y legible.
  • MySQLDialect → le dice a Hibernate qué dialecto SQL usar.
  • batch_size=10 + order_inserts/order_updates → agrupa operaciones en lotes (optimización del batching).
  • generate_statistics=true → muestra estadísticas de Hibernate en consola.
  • NoCachingRegionFactory → declara que NO se usa caché de segundo nivel (contradice a las líneas de cache activadas; son configuraciones de práctica).

6. Paso 4: Entidades — Modelo de datos y relaciones

Las entidades son clases Java que representan tablas. Aquí además vemos relaciones entre tablas.

   usuarios  ——1——————M——  listas_compra  ——1——————M——  items_lista
   (Usuario)                    (ListaCompra)                     (ItemLista)

   productos  (tabla independiente, sin relación)
Tabla / ClaseRelaciónFrase "de negocio"
usuarios—Un usuario existe sin listas.
listas_compra@ManyToOne Usuario + @OneToMany itemsUn usuario tiene muchas listas; una lista pertenece a un usuario. Una lista tiene muchos items.
items_lista@ManyToOne ListaCompraUn item pertenece a una lista.
¿Y por qué existen tablas con nombres distintos a las clases? Porque se usa @Table(name = "..."). La clase ListaCompra → tabla listas_compra, la clase ItemLista → tabla items_lista. Sin @Table, Hibernate usaría el nombre de la clase tal cual.

6.2. Producto.java

Propósito: Guarda nombre, precio y usa @Version para control de concurrencia optimista.
package cibertec.demo.entities;

import jakarta.persistence.*;
import lombok.Data;

@Data
@Entity
@Table(name = "productos")
public class Producto {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;
    private String nombre;
    private Double precio;

    //bloqueo de concurruencia optimista
    @Version
    private Integer version;
}
¿Qué es @Version? Implementa bloqueo optimista: Hibernate incrementa version en cada UPDATE. Si dos peticiones intentan actualizar la misma fila con una versión vieja, la segunda lanza OptimisticLockException. Evita que se sobrescriban cambios entre sí.

6.3. ListaCompra.java

Propósito: Es el centro del modelo: une a un Usuario con sus ItemLista.
package cibertec.demo.entities;

import jakarta.persistence.*;
import lombok.Data;

import java.time.LocalDateTime;
import java.util.List;

@Data
@Entity
@Table(name = "listas_compra")
public class ListaCompra {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;
    private String titulo;
    private LocalDateTime fechaCreacion = LocalDateTime.now();

    @ManyToOne
    private Usuario usuario;

    @OneToMany(mappedBy = "lista", cascade = CascadeType.ALL, orphanRemoval = true)
    private List<ItemLista> items;
}

Anotaciones nuevas

Anotación¿Qué hace?
LocalDateTime fechaCreacion = LocalDateTime.now()Al crear la lista, se asigna automáticamente la fecha/hora actual.
@ManyToOne sobre Usuario"Muchas listas pertenecen a un usuario". Crea una columna FK usuario_id que apunta a usuarios.id.
@OneToMany(mappedBy = "lista", ...)"Una lista tiene muchos items". mappedBy="lista" indica que la relación está definida del otro lado (en ItemLista.lista). El lado @OneToMany es el inverso, no crea columna extra.
cascade = CascadeType.ALLSi guardas una ListaCompra, sus items se guardan automáticamente con ella.
orphanRemoval = trueSi eliminas un item de la lista, ese item se borra de la BD (los "huérfanos" se eliminan).

6.4. ItemLista.java

package cibertec.demo.entities;

import com.fasterxml.jackson.annotation.JsonIgnore;
import jakarta.persistence.*;
import lombok.Data;

@Data
@Entity
@Table(name = "items_lista")
public class ItemLista {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;
    private String nombreProducto;
    private Integer cantidad;
    private String estado = "PENDIENTE";

    @ManyToOne
    @JoinColumn(name = "lista_id")
    @JsonIgnore
    private ListaCompra lista;
}
Elemento¿Qué hace?
String estado = "PENDIENTE"Al crear un item sin especificar estado, se asigna "PENDIENTE" por defecto.
@ManyToOne sobre ListaCompra lista"Muchos items pertenecen a una lista". Este es el lado dueño: aquí se guarda la llave foránea.
@JoinColumn(name = "lista_id")Define el nombre de la columna FK: lista_id.
@JsonIgnoreJackson no incluye el objeto lista al serializar un item. Evita respuestas infinitas o gigantes (item → lista → items → lista...).
Conceptos clave de las relaciones:
  • Lado dueño vs inverso: la FK se guarda en el lado @ManyToOne. El @OneToMany(mappedBy=...) solo "lee" y no crea columnas.
  • mappedBy: apunta al nombre del atributo en la otra clase. Aquí mappedBy="lista" referencia a ItemLista.lista.
  • Cascade: propaga operaciones (guardar, borrar...) de la lista a sus items.
  • @Data y relaciones: genera toString()/equals()/hashCode() con todos los campos; con lazy loading puede dar problemas. En proyectos grandes se usa @Getter @Setter + @ToString.Exclude.

7. Paso 5: Repositorios — Acceso a datos

Los repositorios son interfaces que Spring Data JPA implementa solo. Existen dos formas de definir consultas:

  • Query Methods: Spring interpreta el nombre del método (findByCorreo, findByUsuarioId).
  • @Query (JPQL): escribes la consulta manualmente sobre las clases, con :parametro y @Param.

7.1. UsuarioRepository.java

package cibertec.demo.repository;

import cibertec.demo.entities.Usuario;
import org.springframework.data.jpa.repository.JpaRepository;

import java.util.Optional;

public interface UsuarioRepository extends JpaRepository<Usuario, Long> {
    Optional<Usuario> findByCorreo(String correo);
}

findByCorreo genera SELECT * FROM usuarios WHERE correo = ?. Devuelve Optional porque el correo podría no existir (evita el NullPointerException). Se usa en el login.

7.2. ProductoRepository.java

package cibertec.demo.repository;

import cibertec.demo.entities.Producto;
import org.springframework.data.jpa.repository.JpaRepository;
import org.springframework.data.jpa.repository.Query;
import org.springframework.data.repository.query.Param;

import java.util.List;

public interface ProductoRepository extends JpaRepository<Producto, Long> {
    List<Producto> findByNombre(String nombre);

    @Query("SELECT p FROM Producto p WHERE LOWER(p.nombre) LIKE LOWER(concat('%',:texto,'%'))")
    List<Producto> buscarPorNombre(@Param("texto") String texto);
}
  • findByNombre → búsqueda exacta: WHERE nombre = ?.
  • @Query → búsqueda parcial (LIKE) e insensible a mayúsculas. concat('%',:texto,'%') rodea el texto con %; LOWER(...) fuerza minúsculas de ambos lados.
  • @Param("texto") → conecta el parámetro Java texto con :texto del JPQL.

7.3. ListaCompraRepository.java

package cibertec.demo.repository;

import cibertec.demo.entities.ListaCompra;
import org.springframework.data.domain.Page;
import org.springframework.data.domain.Pageable;
import org.springframework.data.jpa.repository.JpaRepository;

import java.util.List;

public interface ListaCompraRepository extends JpaRepository<ListaCompra, Long> {
    List<ListaCompra> findByUsuarioId(Long idUsuario);
    Page<ListaCompra> findByUsuarioId(Long idUsuario, Pageable pageable);
}

Dos métodos con el mismo nombre pero distinta firma (sobrecarga):

  • Sin Pageable → devuelve List<ListaCompra> (todas). Lo usa el endpoint de historial.
  • Con Pageable → devuelve Page<ListaCompra> (una página, con totales). Lo usan los endpoints paginados.

findByUsuarioId genera WHERE usuario_id = ?. Nota: UsuarioId se refiere al atributo usuario.id (navegación por propiedades).

7.4. ItemListaRepository.java

package cibertec.demo.repository;

import cibertec.demo.entities.ItemLista;
import org.springframework.data.jpa.repository.JpaRepository;
import org.springframework.data.jpa.repository.Query;
import org.springframework.data.repository.query.Param;

import java.util.List;

public interface ItemListaRepository extends JpaRepository<ItemLista, Long> {
    @Query("SELECT i FROM ItemLista i WHERE i.lista.id =:idLista")
    List<ItemLista> detalleLista(@Param("idLista") Long idLista);

    @Query("SELECT i FROM ItemLista i WHERE i.lista.id =:idLista AND i.estado = :estado")
    List<ItemLista> buscarPorEstado(@Param("idLista") Long idLista, @Param("estado") String estado);
}

En JPQL se navega con puntos: i.lista.id equivale a item.lista.id. buscarPorEstado filtra además por estado (PENDIENTE, COMPRADO, etc.).

JPQL vs SQL: JPQL consulta clases y atributos (Producto p, i.estado); SQL consulta tablas y columnas. Hibernate traduce uno a otro.

8. Paso 6: Servicios y utilidades + Dudas resueltas

8.1. UsuarioService.java

Propósito: Lógica de negocio de usuarios: registrar, listar, obtener por id y login.
package cibertec.demo.service;

import cibertec.demo.entities.Usuario;
import cibertec.demo.repository.UsuarioRepository;
import org.springframework.stereotype.Service;

import java.util.List;

@Service
public class UsuarioService {
    private final UsuarioRepository usuarioRepository;

    public UsuarioService(UsuarioRepository usuarioRepository) {
        this.usuarioRepository = usuarioRepository;
    }

    public Usuario registrar(Usuario usuario){
        return usuarioRepository.save(usuario);
    }

    public List<Usuario> listar(){
        return usuarioRepository.findAll();
    }

    public Usuario obtener(Long id){
        return usuarioRepository.findById(id).orElse(null);
    }

    public Usuario login(String correo, String clave){
        Usuario usuario = usuarioRepository.findByCorreo(correo).orElse(null);
        if(usuario != null && usuario.getClave().equals(clave)){
            return usuario;
        }
        return null;
    }
}
  • Inyección por constructor con campo final: patrón recomendado.
  • obtener() usa Optional.orElse(null): si no existe, devuelve null (el controlador decide si responder 404).
  • login(): busca por correo y compara la clave (en este proyecto, en texto plano — el profesor también lo hacía así).
  • Diferencias vs el profesor: yo no copié el import inútil java.util.Stack, y mi método se llama registrar (el profesor tenía registar, un typo).

8.2. ProductoService.java

Propósito: Inserción por lotes (batching) con normalización, listado optimizado y búsqueda.
package cibertec.demo.service;

import cibertec.demo.entities.Producto;
import cibertec.demo.repository.ProductoRepository;
import cibertec.demo.util.FormatoUtil;
import jakarta.persistence.EntityManager;
import jakarta.persistence.PersistenceContext;
import jakarta.transaction.Transactional;
import org.springframework.stereotype.Service;

import java.util.List;

@Service
public class ProductoService {

    private final ProductoRepository productoRepository;
    private final FormatoUtil formatoUtil;

    @PersistenceContext
    private EntityManager em;

    public ProductoService(ProductoRepository productoRepository, FormatoUtil formatoUtil) {
        this.productoRepository = productoRepository;
        this.formatoUtil = formatoUtil;
    }

    //Inserción por lotes (batching)
    @Transactional
    public void registrarLote(List<Producto> productos){
        int i = 0;
        for (Producto p : productos){
            p.setNombre(formatoUtil.capitalizar(p.getNombre()));
            em.persist(p);
            i++;
            if (i % 10 == 0) {
                em.flush();
                em.clear();
            }
        }
    }

    public List<Producto> listarTodos(){
        return em.createQuery("SELECT p FROM Producto p", Producto.class)
                .setHint("org.hibernate.fetchSize", 5)//lee de 5 en 5
                .getResultList();
    }

    public List<Producto> buscar(String nombre){
        return productoRepository.findByNombre(nombre);
    }
}

Elementos clave

Elemento¿Qué hace?
@ServiceMarca la clase como lógica de negocio; Spring la detecta y gestiona.
@PersistenceContext EntityManager emInyecta el gestor de persistencia de JPA para operaciones de bajo nivel (persist, flush, clear, createQuery).
@TransactionalEnvuelve el método en una transacción: si algo falla, se revierte todo. Imprescindible para el batching.
formatoUtil.capitalizar(...)Normaliza el nombre antes de guardarlo (primera letra en mayúscula).
em.persist(p)Marca el producto para inserción (aún no va a la BD).
em.flush() / em.clear()Cada 10 productos: flush envía el lote a la BD y clear limpia la caché de Hibernate.
setHint("org.hibernate.fetchSize", 5)Hint de JDBC: lee los resultados de 5 en 5.
Error común: olvidar @Transactional en registrarLote(). Sin ella, cada persist() haría su propia transacción y el batching perdería su sentido.

package cibertec.demo.util;

8.4. Dudas que me surgieron (resueltas)

¿El constructor se genera solo con IntelliJ?

Sí. Los constructores de inyección son "boilerplate" (código repetitivo) y el IDE los genera. Pasos:

  1. Coloca el cursor sobre la línea de la clase (ej. public class UsuarioService {) o dentro de su cuerpo.
  2. Presiona Alt + Insert (menú Generate).
  3. Elige "Constructor" y marca el campo a inyectar (ej. usuarioRepository).
  4. IntelliJ genera algo como: public UsuarioService(UsuarioRepository usuarioRepository) { this.usuarioRepository = usuarioRepository; }
¿Por qué es obligatorio? Porque el campo es final y en Java un campo final debe asignarse en su declaración o en el constructor. Sin el constructor, el compilador marca: "variable usuarioRepository might not have been initialized". Ese era el error que tenía mi UsuarioService al principio.

¿Y los métodos registrar, listar, obtener, login?

Esos NO se generan automáticamente. El generador de IntelliJ (Alt + Insert) solo crea boilerplate (constructores, getters/setters, equals/hashCode/toString). Los métodos de negocio son tu lógica: IntelliJ no puede saber qué quieres hacer, así que los digitas a mano.

¿De dónde salen esos nombres? No salen de ningún generador: los defines tú. Pero siguen un patrón basado en los métodos que ya existen en JpaRepository:
  • save(...) → de ahí sale registrar(...).
  • findAll() → listar().
  • findById(...).orElse(null) → obtener(id).
  • findByCorreo(...) (método de mi repositorio) → login(...).
O sea: el nombre de cada método del service "envuelve" a un método del repository, dándole significado de negocio.

¿No era el controller quien tenía registrar, listar, etc.?

No, es al revés. Esas firmas viven en el Service. El Controller solo expone el endpoint y llama al service. Ejemplo en mi UsuarioController:

@PostMapping("/registrar")
public ResponseEntity<Usuario> registrar(@RequestBody Usuario usuario){
    Usuario usuarioRegistrado = usuarioService.registrar(usuario);  // <-- llama al SERVICE
    return ResponseEntity.ok(usuarioRegistrado);
}
Resumen de la duda:
  • Constructor → se GENERA con Alt + Insert (boilerplate, "esqueleto").
  • Métodos de negocio → se DIGITAN a mano (lógica, "órganos"). El generador no los crea.
  • Controller vs Service → el controller llama, el service implementa.

package cibertec.demo.controllers;

10.3. ProductoController.java

package cibertec.demo.controllers;

import cibertec.demo.entities.Producto;
import cibertec.demo.repository.ProductoRepository;
import cibertec.demo.service.ProductoService;
import org.springframework.http.ResponseEntity;
import org.springframework.web.bind.annotation.*;

import java.util.List;

@RestController
@RequestMapping("/api/productos")
public class ProductoController {

    private final ProductoService productoService;
    private final ProductoRepository productoRepository;

    public ProductoController(ProductoService productoService, ProductoRepository productoRepository) {
        this.productoService = productoService;
        this.productoRepository = productoRepository;
    }

    @PostMapping("/lote")
    public ResponseEntity<String> registrarLote(@RequestBody List<Producto> productos){
        productoService.registrarLote(productos);
        return ResponseEntity.ok("Productos registrados satisfactoriamente");
    }

    @GetMapping
    public List<Producto> listar(){
        return productoService.listarTodos();
    }

    @GetMapping("/{id}")
    public ResponseEntity<Producto> obtenerPorId(@PathVariable Long id){
        return productoRepository.findById(id)
                .map(ResponseEntity::ok)
                .orElse(ResponseEntity.notFound().build());
    }

    @GetMapping("/buscar/{nombre}")
    public List<Producto> buscarPorNombre(@PathVariable String nombre){
        return productoService.buscar(nombre);
    }

    @PutMapping("/{id}")
    public ResponseEntity<Producto> actualizar(@PathVariable Long id, @RequestBody Producto producto){
        return productoRepository.findById(id)
                .map(prod -> {
                    prod.setNombre(producto.getNombre());
                    prod.setPrecio(producto.getPrecio());
                    Producto actualizado = productoRepository.save(prod);
                    return ResponseEntity.ok(actualizado);
                })
                .orElse(ResponseEntity.notFound().build());
    }

    @GetMapping("/buscarPorNombre")
    public ResponseEntity<List<Producto>> buscarPorNombreParam(@RequestParam String texto){
        List<Producto> resultados = productoRepository.buscarPorNombre(texto);
        if(resultados.isEmpty()){
            return ResponseEntity.notFound().build();
        }
        return ResponseEntity.ok(resultados);
    }
}
Error que tuve y corregí: el método actualizar lo había anotado con @GetMapping("/{id}"). Como ya existe obtenerPorId con la misma ruta, se producía un "Ambiguous mapping" y la app no arrancaba. La solución: actualizar debe ser @PutMapping("/{id}"). PUT = actualizar; GET = consultar.

@PathVariable vs @RequestParam

@PathVariable lee de la ruta: /buscar/Laptop → nombre="Laptop".
@RequestParam lee del query string: /buscarPorNombre?texto=Lap → texto="Lap".

10.4. ListaCompraController.java

Propósito: El controlador más completo. Gestiona listas de compra, sus items, estados, historial y paginación con ordenamiento.
package cibertec.demo.controllers;

import cibertec.demo.entities.ItemLista;
import cibertec.demo.entities.ListaCompra;
import cibertec.demo.entities.Usuario;
import cibertec.demo.repository.ItemListaRepository;
import cibertec.demo.repository.ListaCompraRepository;
import cibertec.demo.repository.UsuarioRepository;
import org.springframework.data.domain.Page;
import org.springframework.data.domain.PageRequest;
import org.springframework.data.domain.Pageable;
import org.springframework.data.domain.Sort;
import org.springframework.http.ResponseEntity;
import org.springframework.web.bind.annotation.*;

import java.util.List;

@RestController
@RequestMapping("/api/listas")
public class ListaCompraController {

    private final UsuarioRepository usuarioRepository;
    private final ListaCompraRepository listaCompraRepository;
    private final ItemListaRepository itemListaRepository;

    public ListaCompraController(UsuarioRepository usuarioRepository, ListaCompraRepository listaCompraRepository, ItemListaRepository itemListaRepository) {
        this.usuarioRepository = usuarioRepository;
        this.listaCompraRepository = listaCompraRepository;
        this.itemListaRepository = itemListaRepository;
    }

    //Crea una lista SOLO si el usuario existe
    @PostMapping("/{idUsuario}/crear")
    public ResponseEntity<?> crear(@PathVariable Long idUsuario, @RequestBody ListaCompra listaCompra){
        Usuario usuario = usuarioRepository.findById(idUsuario).orElse(null);
        if(usuario == null){
            return ResponseEntity.badRequest().body("Usuario no encontrado");
        }
        listaCompra.setUsuario(usuario);
        return ResponseEntity.ok(listaCompraRepository.save(listaCompra));
    }

    @PostMapping("/{idLista}/agregar-item")
    public ResponseEntity<?> agregarItem(@PathVariable Long idLista, @RequestBody ItemLista itemLista){
        ListaCompra listaCompra = listaCompraRepository.findById(idLista).orElse(null);
        if(listaCompra == null){
            return ResponseEntity.notFound().build();
        }
        itemLista.setLista(listaCompra);
        return ResponseEntity.ok(itemListaRepository.save(itemLista));
    }

    @PutMapping("/item/{idItem}/estado")
    public ResponseEntity<?> cambiarEstado(@PathVariable Long idItem, @RequestParam String estado){
        return itemListaRepository.findById(idItem)
                .map(item ->{
                    item.setEstado(estado);
                    return ResponseEntity.ok(itemListaRepository.save(item));
                }).orElse(ResponseEntity.notFound().build());
    }

    @GetMapping("usuario/{idUsuario}")
    public List<ListaCompra> historial(@PathVariable Long idUsuario){
        return listaCompraRepository.findByUsuarioId(idUsuario);
    }

    @GetMapping("/{idLista}")
    public ResponseEntity<List<ItemLista>> detalle(@PathVariable Long idLista){
        List<ItemLista> items = itemListaRepository.detalleLista(idLista);
        if (items.isEmpty()){
            return ResponseEntity.noContent().build();
        }
        return ResponseEntity.ok(items);
    }

    @GetMapping("/{idLista}/items")
    public ResponseEntity<List<ItemLista>> obtenerItemsPorEstado(@PathVariable Long idLista, @RequestParam String estado){
        List<ItemLista> items = itemListaRepository.buscarPorEstado(idLista, estado);
        if(items.isEmpty()){
            return ResponseEntity.noContent().build();
        }
        return ResponseEntity.ok(items);
    }

    @GetMapping("/usuario/{idUsuario}/paginado")
    public Page<ListaCompra> historialPaginado(@PathVariable Long idUsuario, @RequestParam int page, @RequestParam int size){
        Pageable pageable = PageRequest.of(page, size);
        return listaCompraRepository.findByUsuarioId(idUsuario, pageable);
    }

    @GetMapping("/usuario/{idUsuario}/paginado/ordenado")
    public Page<ListaCompra> historialPaginadoOrdenado(
            @PathVariable Long idUsuario,
            @RequestParam int page,
            @RequestParam int size,
            @RequestParam(defaultValue = "fechaCreacion") String sortBy,
            @RequestParam(defaultValue = "desc") String order
    ){
        Sort sort = order.equalsIgnoreCase("asc") ?
                Sort.by(sortBy).ascending() :
                Sort.by(sortBy).descending();
        Pageable pageable = PageRequest.of(page, size, sort);
        return listaCompraRepository.findByUsuarioId(idUsuario, pageable);
    }
}
Error que tuve y corregí: al agregar el método historial, lo puse con @GetMapping("/{idLista}") (la misma ruta que detalle) → mapeo ambiguo. La solución: historial usa @GetMapping("usuario/{idUsuario}"). Ojo: ese es el único @GetMapping del proyecto que no empieza con / (así lo tiene el profesor, y funciona porque el prefijo base /api/listas ya lo completa). En general, mejor poner siempre la / inicial.

Paginación: Pageable, PageRequest y Sort

  • Pageable → interfaz que representa "qué página y cuántos elementos" (más ordenamiento).
  • PageRequest.of(page, size) → implementación básica: página page (empieza en 0) y size elementos por página.
  • PageRequest.of(page, size, sort) → versión con ordenamiento.
  • Sort.by("campo").ascending() → ordena por el campo indicado; descending() al revés.
  • Page<T> → la respuesta incluye: content (los datos), totalElements, totalPages, number, size, etc.

package cibertec.demo.config;

13. Resumen: orden de creación, pendientes y comandos

Paso 1: Proyecto Maven simple ("pelado") en IntelliJ. pom.xml con parent Spring Boot 4.0.7 y dependencias: Web, Data JPA, Lombok, DevTools, MySQL 8.3.0, Security.
Paso 2: application.properties: puerto 8080, MySQL localhost:3306/cibertec_demo, ddl-auto=create, show-sql, batching. Levanta XAMPP (Apache + MySQL) y crea la base cibertec_demo en phpMyAdmin.
Paso 3: Clase principal ReplicaAntesT2Application en cibertec.demo.
Paso 4: Entidades: Usuario, Producto (con @Version), ListaCompra (relaciones + cascade + orphanRemoval), ItemLista (@JoinColumn + @JsonIgnore).
Paso 5: Repositorios: 4 interfaces que extienden JpaRepository. Query Methods (findByCorreo, findByNombre, findByUsuarioId) y @Query JPQL con @Param.
Paso 6: Servicios + util: UsuarioService (constructor con Alt + Insert, métodos a mano), ProductoService (batching), FormatoUtil con @Component.
Paso 7: DTO LoginRequest (correo, clave).
Paso 8: Controladores: AuthController, UsuarioController, ProductoController, ListaCompraController (18 endpoints).
Paso 9: Config: SecurityConfig (usuarios en memoria + BCrypt), LoginInterceptor, WebConfig con @Configuration.
Paso 10: Correr ReplicaAntesT2Application.main(), esperar "Started ReplicaAntesT2Application", y probar con Postman (Basic Auth admin/admin123).
